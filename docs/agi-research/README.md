## Roadmap context (Levels, a direction not a claim of achievement)

- **Level 1 — Information:** knowledge, search, analysis, memory, retrieval.
- **Level 2 — Autonomous engineering (development target):** planning, coding, tool creation, execution, testing, simulation.
- **Level 3 — General intelligence research (long-term vision):** discovery, novel algorithms, scientific research, cross-domain reasoning, verified knowledge.

Nobody may claim AGI or Level 3 has been reached without reproducible benchmarks.

## Project facts a new instance needs (verify before relying on them)

- Two repos under `C:\dev\AGI\DARK-AGI-WINDOWS\`: `dark-agi-backend` (authoritative enforcement: scope, approval, audit, roles, execution engine) and `dark-agi-frontend` (Next.js 16, React 19, TypeScript, Tailwind 4, SWR, Vitest, API types generated by openapi-typescript).
- Next.js here has breaking changes; read `node_modules/next/dist/docs/` before writing Next-specific code.
- Command language: `dagi <verb> key=value … keng`, in `src/lib/commands.ts` (132 aliases at time of writing). Commands are parsed to `{toolId, operationId, input}` and POSTed as jobs. They are never run as a shell.
- Gates on a job: scope (network ops), approval (`requiresApproval`), availability (`available` / `unavailableReason`; `planned` ops cannot run), input schema, role permissions, remote-host authorization (for `remote:*`), hash-chained audit.
- The frontend only displays and submits; it must never be relied on for enforcement. Backend behavior has NOT been verified from the frontend side; inspect `dark-agi-backend` before designing anything that touches execution or storage.
- Console modules are listed in `src/lib/modules.ts` (`live` vs `planned`).
- Work so far at the time of writing is on branch `feat/asset-authorization-ui`.

## Working rules for every instance

1. Follow the Master Directive's non-negotiable security rules. Do not weaken scope, approval, authorization, or audit.
2. Do not overwrite uncommitted user work. Check `git status` first.
3. Separate verified facts, proposals, and speculation. Never report unexecuted tests as passed.
4. Independent verification: do not let a component be the sole judge of its own result.
5. Record outputs of each mission under `docs/agi-research/output/mission-XX-*.md` (create the folder when needed), and update the status table below before stopping.
6. Before significant architectural change or any database/schema change, get user approval.
